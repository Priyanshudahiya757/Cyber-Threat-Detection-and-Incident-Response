CYBER THREAT DETECTION AND INCIDENT RESPONSE DASHBOARD
========================================================

Purpose
-------
This project is a local SOC dashboard and lightweight SIEM demonstration.
It ingests security logs, normalizes them, detects threats with rules and
machine learning, creates alerts and incidents, and gives analysts a web UI
for investigation.

Scope
-----
- Local academic/demo deployment.
- Four supported log sources: Linux, Windows, firewall, and web server.
- Rule detection plus Isolation Forest anomaly detection.
- Incident correlation and analyst workflow.
- Not hardened for direct public production use without security work.

6. LOGIN WORKFLOW
-----------------
1. Open http://localhost:5173.
2. Enter the seeded admin username and password.
3. Select Remember Me if the browser should persist tokens locally.
4. Submit login.
5. Frontend calls POST /api/v1/auth/login.
6. Backend checks the user in MongoDB and verifies the bcrypt password hash.
7. Backend returns access and refresh JWT tokens plus public user data.
8. Frontend stores tokens in localStorage or sessionStorage.
9. Protected routes become available according to user role.

Session behavior:
- Axios attaches the access token to API requests.
- A failed access token can trigger one refresh request.
- Refresh success retries the original request.
- Refresh failure clears tokens and returns the user to /login.
- Logout removes stored tokens and clears current user state.

Roles:
- admin: full access, including user management, rule changes, and ML training.
- soc_analyst: investigation and monitoring access without admin-only actions.


7. FRONTEND FEATURES
--------------------
Dashboard
  Route: /dashboard
  Shows total logs, detected threats, active incidents, critical alerts, and
  AI anomalies. Charts show threat timeline, severity distribution, attack
  types, top source IPs, and recent events. React Query refreshes dashboard
  data every 15 seconds.

Live Monitoring
  Route: /live-monitoring
  Searches normalized Elasticsearch logs. Analysts can inspect timestamps,
  source type, source host, source IP, destination, action, severity, and raw
  evidence.

Upload Logs
  Route: /upload-logs
  Uploads .log, .txt, or .json files through multipart HTTP. Select source
  type and source host. Backend validates file type, UTF-8 content, and the
  configured maximum file size. Accepted logs enter the full pipeline.

Threat Detection
  Route: /threat-detection
  Lists rule and ML DetectionEvent records. Analysts can filter or inspect
  severity, detection engine, rule name, MITRE mapping, entity, confidence,
  explanation, and evidence IDs. A manual detection run can be started where
  permitted by the API.

AI Anomaly Detection
  Route: /anomaly-detection
  Displays model metadata, training status, anomaly scores, and prediction
  results. Admin users can train a model. Analysts with permission can run
  prediction and inspect model results.

  Training needs at least five distinct source IP entities. A demo seed may
  skip training when all uploaded logs are duplicates or contain too few
  distinct entities. Existing models remain available in ml/models.

Incident Management
  Route: /incidents
  Converts related detections into incidents. Analysts can inspect evidence,
  assign an analyst, add investigation notes, change status, resolve, and
  close incidents. Typical status flow:

    OPEN -> INVESTIGATING -> RESOLVED -> CLOSED

  Incidents are not deleted; history and notes support auditability.

Analytics
  Route: /analytics
  Combines Elasticsearch telemetry with MongoDB operational records. Provides
  time trends, severity counts, attack types, source IP rankings, and summary
  metrics for reporting and investigation.

Detection Rules
  Route: /detection-rules
  Lists registered rules and their enabled state. Admin users can enable or
  disable rules. Rule state is persisted in MongoDB and loaded at backend
  startup.

User Management
  Route: /users
  Admin-only page. Creates users and manages role-related user operations
  through protected API routes.

Settings
  Route: /settings
  Displays application and account-oriented settings available to the current
  user. Sensitive backend secrets are never exposed through this page.


8. LOG PROCESSING FLOW
----------------------
1. User uploads a log file or a client sends JSON to /api/v1/logs/ingest.
2. API validates source type, file extension, size, and encoding.
3. IngestionPipeline selects parser from PARSER_REGISTRY.
4. Parser extracts source-specific fields and preserves raw evidence.
5. Normalizer creates a canonical NormalizedLog object.
6. Timestamp becomes UTC and severity receives a validated value or LOW.
7. SHA-256 content identity creates deterministic log_id.
8. Elasticsearch duplicate search prevents re-ingestion.
9. New normalized logs are bulk-indexed in security-logs-YYYY.MM.DD.
10. MongoDB stores an ingestion batch audit record.
11. Detection callback runs enabled rules and ML prediction.
12. DetectionEvent records are stored in MongoDB.
13. High and critical detections create Alert records.
14. Correlator groups related detections into existing or new incidents.
15. Frontend queries API data and refreshes dashboard views.

Parser coverage:
- Linux: SSH authentication and sudo activity.
- Windows: Security JSON and common Event IDs such as 4624, 4625, 4672,
  4720, and 4728.
- Firewall: allow/deny, protocol, source, destination, and port fields.
- Web server: Apache/Nginx Combined Log Format and attack payload scanning.


9. DETECTION TECHNOLOGY
-----------------------
Rule engine
  Python modular rules implement known attack patterns. Current coverage
  includes SSH brute force, Windows failed login, port scan, SQL injection,
  cross-site scripting, directory traversal, privilege escalation, and
  suspicious administrator login.

  Each rule can produce severity, confidence, explanation, MITRE ATT&CK
  mapping, entity value, and evidence references. Rule failures are isolated
  so one broken rule does not stop the whole detection batch.

Machine learning
  Isolation Forest detects unusual behavior from source-IP feature vectors.
  Feature extraction summarizes activity such as counts, failure ratios,
  ports, protocols, and time patterns. Models are stored as versioned joblib
  artifacts and tracked through the model registry.

  ML endpoints:
  - POST /api/v1/ml/train
  - POST /api/v1/ml/predict
  - GET  /api/v1/ml/models
  - GET  /api/v1/ml/models/latest
  - POST /api/v1/ml/evaluate

Alerts
  High and critical detections become MongoDB Alert records. External email,
  Discord, and Telegram dispatch configuration exists as future integration
  scope; in-application alert records are implemented.


10. DATA STORAGE
----------------
MongoDB stores mutable application records:
- users
- detections
- alerts
- incidents
- ingestion_batches
- detection_rules
- counters for incident IDs

Elasticsearch stores normalized security telemetry:
- daily security-logs-* indices
- raw log evidence
- structured fields for filtering and aggregation
- duplicate checks by log_id

Docker named volumes preserve data:
- mongo_data
- es_data

Stop containers without deleting data:

  docker compose down

Start again with existing data:

  docker compose up -d

Do not use `docker compose down -v` unless permanent database deletion is
intended. That command removes named volumes and all stored MongoDB and
Elasticsearch data.

12. TECHNOLOGY STACK
--------------------
Frontend:
- React 18: component UI and application state boundaries.
- TypeScript: typed props, API responses, and feature contracts.
- Vite: development server, proxy, and production bundling.
- React Router: protected routes and admin route guard.
- TanStack Query: server-state fetching, caching, mutations, and refresh.
- Axios: HTTP client, JWT attachment, refresh retry, and API boundary.
- React Hook Form and Zod: form state and validation.
- Tailwind CSS: visual tokens and utility styling.
- Recharts: dashboard and analytics charts.
- lucide-react: interface icons.

Backend:
- FastAPI: async HTTP API and OpenAPI documentation.
- Pydantic: request, response, and normalized log schemas.
- Uvicorn: ASGI server.
- Motor: async MongoDB driver.
- Elasticsearch async client: log indexing, searching, and aggregations.
- Passlib and bcrypt: password hashing and verification.
- python-jose: JWT access and refresh tokens.
- scikit-learn: Isolation Forest model.
- pandas and NumPy: ML feature and dataset processing.
- joblib: model artifact persistence.

Operations:
- Docker Compose: repeatable multi-service local deployment.
- MongoDB: workflow and identity records.
- Elasticsearch: high-volume searchable log evidence.
- Kibana: optional Elasticsearch inspection UI.
- Cloudflare Quick Tunnel: free temporary public access for demos.

Architecture pattern:
  React UI -> Axios API client -> FastAPI routers -> services/repositories
  -> MongoDB and Elasticsearch

Ingestion dependency direction:
  Ingestion pipeline -> registered detection callback -> rule engine and ML

This keeps ingestion independent from detection implementation details.

15. TROUBLESHOOTING
-------------------
Docker daemon unavailable:
  Start Docker Desktop, then run docker info and docker compose up -d.

Services unhealthy:
  docker compose ps
  docker compose logs backend
  docker compose logs elasticsearch
  docker compose logs mongo

Frontend host blocked with 403:
  Confirm frontend/vite.config.ts includes .trycloudflare.com in allowedHosts.
  Rebuild frontend:
    docker compose up -d --build frontend

Login fails:
- Confirm seed_admin.py ran.
- Confirm SEED_ADMIN_USERNAME and SEED_ADMIN_PASSWORD in backend/.env.
- Check backend logs.

No detections:
- Confirm logs were accepted rather than marked duplicates.
- Check source_type matches a supported parser.
- Check enabled rules on Detection Rules page.
- Inspect backend logs.

ML training returns 422:
- Training requires at least five distinct source IPs.
- Use varied logs or evaluate the included labeled dataset instead.

Public tunnel fails:
- Keep Docker services running.
- Keep cloudflared process running.
- Verify http://localhost:5173 works locally first.
